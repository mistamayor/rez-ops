02

Disney Method

technique · divergent

three roomsDreamer imagines without limits, Realist grounds it in what can actually ship, Critic stress-tests both.

Dreamer

  • The agent watches every system change org-wide and silently re-runs the whole dependency and impact model before anyone asks.
  • It drafts the DR test schedule for the year, negotiates slots via every app owner's calendar API, and just tells you when to show up.
  • It writes the audit report, the compliance evidence pack, and the board deck, and only asks you to sign off.
  • One daily voice/text briefing — what changed, what is now at risk, who to ping, the exact message to send them.

Realist

  • Start with read-only connectors (CMDB, ticketing, git, calendar) before ever writing back to a system of record.
  • Human approval gate before anything touches a runbook, RACI, or schedule a real incident would depend on.
  • Persist state in a git repo (memory-as-code) so every change to the DR program has a diff, an author, and a revert.
  • One MCP server per domain (BIA, CMDB, ticketing, calendar) behind a single orchestrating agent so connectors swap independently.

Critic

  • Nobody trusts an AI-derived dependency map until it is wrong once loudly — build confidence scoring and show-your-sources into every inferred link.
  • Auditors want a human-signed trail, not "the agent decided" — every automated action needs an attributable human approver.
  • A CMDB is often already stale, so the agent inherits garbage-in unless it cross-validates across at least two sources before flagging.
  • Over-automation risk — if the daily briefing becomes noise people stop reading it, so the agent must learn to shut up about the 90% that has not changed.
03

Five Whys

technique · root-cause

drill-downWhy are DR programs reactive? Five descents to the root.

Why 1

DR programs are reactive because status only gets checked right before an audit or after an incident.

Why 2

It is only checked then because compiling current state (BIA, tests, ownership) is manual and slow.

Why 3

Compiling it is slow because the data lives in disconnected systems with no shared freshness signal.

Why 4

There is no shared freshness signal because nothing owns staleness as a first-class concept — tools store data but not its expiry.

Why 5

Nothing owns staleness because DR artifacts were designed as one-time deliverables, not living, continuously-revalidated state.

root cause

DR is treated as a project, not a system with a heartbeat — the agent's core job is to give staleness a heartbeat per artifact type and tier.

insight
Compliance evidence-gathering hurts for the same root reason: it is reconstructed retroactively from memory and scattered emails instead of captured live.

Assumption Reversal

technique · divergent

mirror flipState the standing assumption, then flip it and see what's true instead.

assumption

DR data lives in dedicated DR tools.

⇄
reversed

It lives scattered in the systems it protects (git, CMDBs, calendars) and the agent is pure aggregation, never a new system of record.

assumption

A human must review every flagged staleness item.

⇄
reversed

The agent auto-resolves low-risk staleness itself (e.g. dry-runs a Tier-3 runbook to reverify accuracy) and only escalates what it cannot verify.

assumption

The program manager drives the schedule.

⇄
reversed

The schedule drives the program manager — the agent negotiates and locks calendar slots directly with owners, PM only intervenes on conflict.

assumption

Dependency mapping requires manual CMDB curation.

⇄
reversed

Maps are inferred continuously from network flow logs, deploy pipelines, and API call graphs — the CMDB becomes a confirmation layer, not the source.

assumption

Greenfield and brownfield need different tools.

⇄
reversed

Brownfield is greenfield with pre-loaded, lower-confidence memory — the adoption audit pass IS the greenfield bootstrap, just seeded with existing data to validate.

assumption

More data sources is always better.

⇄
reversed

Fewer, higher-trust sources with strong provenance beat many low-trust feeds — rank and red-line sources by trust score, not breadth.

assumption

The agent always notifies the person.

⇄
reversed

Sometimes the agent should notify the system (auto-file a ticket, auto-update a status field) and only loop in a human on exception.

06

Observer Effect

technique · systems

the watching changes the watchedInstalling the agent changes the behavior of the system it observes.

If the agent scores app owners on responsiveness, owners may game the metric with fast empty acknowledgements rather than genuinely engaging.

Once dependency mapping is visible and shared, teams may deliberately hide or under-document risky dependencies to avoid being flagged as a blocker.

Once a staleness score exists and is watched, teams optimize the score (touch the doc to reset a timestamp) rather than the underlying accuracy — must detect refreshed-but-not-reviewed via content diff, not just mtime.

Simply installing a DR agent that watches everything may itself raise perceived audit pressure and change how honestly people log incidents — needs transparent, non-punitive framing or it corrupts its own data.

The daily catch-up ritual itself may narrow DR maturity to whatever the agent's brief measures — scope creep toward the instrumentable, not the important.

If leadership sees a shiny DR maturity score rise, budget/attention for DR might paradoxically decrease because "it is handled now" — the dashboard's success could starve its own resourcing.

Publishing a dependency graph might reveal politically inconvenient ownership gaps (two teams each think the other owns something) — needs a diplomatic communication layer, not a raw graph dump.

Six Thinking Hats

technique · parallel lenses

six lenses, one topicSame question, six deliberately different modes of thought.

White · facts

Today's real inputs are BIA docs, app inventory/tiering, runbooks, playbooks, RACI, test schedules — mostly manual, mostly stale, mostly scattered.

Red · feelings

Want to feel lazy — covered, not chasing people — and confident nothing is missed.

Yellow · benefits

Proactive flagging could catch a Tier-1 app with no reviewed BIA in 18 months before an auditor or an actual outage does.

Black · risks

False confidence — if the agent's coverage has blind spots, you might trust it more than the data deserves.

Green · new idea

A confidence coverage map showing which domains/tiers are agent-verified vs still manual/unknown, so blind spots are visible, not hidden.

Blue · process

Run the program at agent-native cadence — daily micro-check, weekly digest, monthly deep audit, quarterly leadership report — different loop speeds for different stakeholders.

Kill the Crown Jewel

technique · destructive

delete the favorite, see what regrowsThe most-loved feature is removed on purpose to find what actually matters underneath it.

the daily notification / catch-up
what grew back
  • Without a daily push, the agent becomes pull-based: an always-current state-of-the-program dashboard/chat command, plus event-triggered alerts only for genuinely urgent risk.
  • The real value surfaces as the memory and dependency graph itself — a living queryable model any tool (chat, dashboard, ticketing bot) can read from; the notification was just one view on that model.
  • Design implication: build the state model and connectors first as the core product; daily catch-up becomes just the default delivery channel, swappable for Slack digest, email, or on-demand voice briefing.
  • Without the notification, laziness has to be re-earned through radical query-ability — a natural language chat interface ("what is stale", "what is due", "what needs me") becomes the crown-jewel replacement.

Blast Radius Rewind

technique · invented, brand new

Take a real past incident or change, rewind it in a sandbox against the agent's current dependency model, check whether the agent would have flagged the risk before it happened, and mine what data or connection was missing.

  • Feed the agent 3 anonymized past incidents/changes as unit tests for the dependency model — whatever it would not have caught IS the connector priority list.
  • Turn every real incident retro into a permanent regression test for the agent's model, so its accuracy is provably improving over time, not just asserted.
  • Score the agent's model retroactively against every incident in the last 3 years as a standing "would-have-caught-it" scoreboard, published alongside its live claims for credibility.

Ownerless Object Hunt

technique · invented, brand new
?

For every artifact/system the agent touches, systematically ask: if this had no listed owner today, who would the agent guess, and how confident is it? Surfaces orphaned ownership before it becomes a crisis.

  • The agent maintains a live orphan-risk list — systems where RACI says one thing but recent activity (commits, tickets, on-call) says another, or nothing at all.
  • Confidence-scored owner inference lets the agent auto-draft (never auto-send) the "are-you-still-the-owner-of-X" message for a human to approve and fire.
  • Cross-reference org-chart/HRIS changes (leavers, team moves) against RACI nightly — a departed owner becomes a guaranteed orphan caught the day it happens, not the day someone needs them.

Ecosystem Thinking

technique · biomimetic, chosen for the goal

the DR program as a living ecosystemMap the program onto biological roles to find forces a purely mechanical model misses.

predators / competition

Incident response teams and the DR program compete for the same on-call attention — the agent should coordinate timing so DR drills never collide with live incident load.

symbiosis

The agent should partner with existing tools (ticketing, CMDB, calendar) rather than replace them — connective tissue, not a new organ competing for the same niche.

decomposers

Stale runbooks and BIAs are the dead matter — the agent's staleness-flagging role IS the decomposer function, breaking outdated artifacts back into needs-regeneration so accurate info recirculates.

keystone species

App/service tiering is the keystone — get tiering wrong and the whole priority signal collapses, so tiering itself should be a high-value, frequently-revalidated artifact, not a one-time classification.

migration / gaps

Org restructures and team moves create sudden ownership migration gaps — watch org-chart/team-topology changes as a leading indicator RACI is about to go stale, do not wait for the RACI doc itself to be flagged.

invasive species

Shadow-IT systems (unsanctioned SaaS/tools) are untracked, undocumented, and usually the actual cause of an unmapped dependency — hunt them via expense/SSO logs.

Role Playing

technique · collaborative, chosen for the goal

six stakeholders, six demandsSpeak the requirement in each stakeholder's own voice.

app owner (technical)

I do not want another dashboard to check — ping me in Slack with exactly what changed and what you need from me, one line, with a deadline.

business stakeholder

I care about risk in business terms — revenue at risk or customers impacted, not "RTO breached by 4 hours" — translate technical staleness into business exposure.

compliance / audit

Show me evidence, not intentions — a timestamped, immutable trail of who reviewed what and when, exportable on demand, or it does not count.

DR program owner (Olu)

Tell me only what needs a decision from me today, ranked by risk, with the action already drafted (message, ticket, escalation) so all I do is approve.

skeptical CISO

Prove the AI is not hallucinating a dependency — every automated claim needs a clickable source, or I will not sign off on using this for compliance evidence.

new hire

I inherited this DR program with zero context — I want the agent to onboard ME: here is the current state, here is what is overdue, here is who is who.

Synthesis I — Signal Convergence

six lines of evidence, one direction

six techniques, run independently, kept landing on the same six truths

Convergence 1 · strongest signal

Freshness Ledger (invented) + staleness-heartbeat root cause (Five Whys) + hard-expire-by-default (Provocation) are the same discovery from three angles — staleness must be a first-class, structured, expiring data model, not a vibe.

Convergence 2 · architecture

Runbooks-as-cache (Provocation) + memory-as-code in git (Disney Realist) + ledger-as-compliance-artifact (Freshness Ledger) sketch the actual architecture — git-backed memory, live-regenerated artifacts, ledger doubling as the audit trail.

Convergence 3 · ownership

RACI × MCP (Solution Matrix) + Ownerless Object Hunt (invented) + org-migration-gaps (Ecosystem) + three separate Role Playing voices all point at ownership as the single most fragile, highest-leverage data domain — more urgent to solve than BIA or runbooks because everything else depends on knowing who to ping right now.

Convergence 4 · product shape

Kill the Crown Jewel (state model as core product, notification as a swappable view) + Blast Radius Rewind (retroactive would-have-caught-it scoreboard) converge on the product being a trust-building live model, not a notification bot — the daily catch-up is the friendliest UI on top of a verifiable state machine.

Convergence 5 · trust as a parameter

The Observer Effect risk cluster (gamed staleness scores, hidden dependencies, notification fatigue, budget starving its own success) plus the Role Playing demands for non-punitive evidence-based framing means trust and psychological safety must be a first-class design parameter, not an afterthought.

Convergence 6 · honest scope

Confidence coverage map (Six Hats) + the BIA-Git and Scheduling-Git gaps (Solution Matrix) + read-only-first (Disney Realist) define a natural, honest v1 scope: an agent that is upfront about what it can and cannot see yet.

proposed v1 direction

Where all six signals converge

  • Git-backed memory + Freshness Ledger data model + read-only connectors (calendar, ticketing, git, CMDB) + confidence/coverage map.
  • Signature UI is chat-queryable state; the daily digest is just one view on it.
  • Ownership-fragility (RACI-via-activity-inference + Ownerless Object Hunt) is the wedge feature.
  • Trust layer — show-your-sources, non-punitive framing, human-approval gate on writes — is required before compliance/CISO stakeholders will accept it.
  • Blast Radius Rewind and proactive micro-drills come later, once trust is established.

Time Shifting

technique · creative, random draw

same harvest, different centuriesSolve the same problem as a 1900s artisan, then again as a 2150 colonist.

1900s · artisan harvest

A meticulous ledger-keeper apprentice visits every workshop on a fixed rota, one master book, flags anything unre-inspected within its season — the master-ledger-as-single-source-of-truth and fixed visiting cadence are timeless ideas worth keeping even in the AI version.

2150 · colonist harvest

  • Colonies fail together or not at all — treat every dependency as an existential coupling, not a technical footnote; dependency mapping is survival infrastructure, not a nice-to-have.

Elemental Forces

technique · wild, random draw

four forces, four lensesFire, water, earth, air — what does each classical element demand of the design?

fire

Burns away any artifact that cannot prove it has been touched in N months — force automatic archival/hiding of unverified content so only trusted, live data is shown by default.

water

Reveals real dependency paths by following where data/traffic actually flows, like water finds the crack — reinforces inferring dependencies from actual flow, not declared diagrams.

earth

The tiering model is the foundation — the slowest-changing, most load-bearing layer; schedules and notifications sit on top and should not be allowed to silently drift from it.

air

The notification/comms layer is invisible until needed but carries the who-to-engage signal — if this layer is polluted with noise, nothing else works no matter how good the rest is.

Ancestor Council

technique · cultural, random draw

three elders, three eras of hard-won judgmentSummon practitioners from different eras of computing and ask each for a verdict.

COBOL mainframe ops elder

Document everything on paper as backup, never trust a system that cannot survive its own outage — the agent's own memory must be recoverable without the agent (git and plain files, not a proprietary DB); the DR tool must itself be disaster-recoverable.

Silicon Valley startup elder

Ship fast, iterate, do not wait for perfect data — launch read-only and useful on partial/messy data immediately rather than waiting for a clean, fully-integrated model.

Compliance / audit elder

If it is not written down and signed, it did not happen — no automated action counts as done without a durable, attributable, timestamped record, non-negotiable.

reconciliation

Fast-to-start, provably durable, and self-recoverable are not actually in tension — launch narrow and read-only fast, but log everything to durable, human-readable, git-backed records from day one.

Devil's Advocate Courtroom

technique · theatrical, random draw

prosecution vs. defensePut the whole concept on trial — argue against it as hard as for it, then render a verdict.

Prosecution

  • The agent creates a single point of failure — if it is wrong or down, the DR program is blind, ironic for a disaster-recovery tool.
  • It will produce false confidence — people stop doing real reviews because "the agent has got it."

Defense

  • It is additive not a replacement — every connector is read-only-first and the underlying systems of record still exist; the agent going down just means you are back to today's manual baseline, not worse off.
  • The confidence/coverage map explicitly shows agent-verified vs. unknown, and the agent escalates uncertainty rather than papering over it — the antidote to false confidence is designed in, not bolted on.
verdict

Guilty of introducing a new dependency, but net risk-reducing IF it is read-only and gracefully degrades to today's baseline when down, AND never hides its own uncertainty — both should be hard, non-negotiable design constraints, not aspirations.

positioning line

Smoke detector, not fire inspector

Captures the whole product's positioning in one line (Drunk History Retelling): continuous ambient detection instead of scheduled, high-ceremony inspection.

The Ancestor Council and the Devil's Advocate Courtroom verdict converge, independently, on the same four non-negotiables:

  • Read-only-first — write access is earned, never assumed.
  • Graceful degradation — if the agent is wrong or down, you are back to today's manual baseline, never worse off.
  • Self-recoverable memory — durable, human-readable, git-backed records; the DR tool must itself be disaster-recoverable.
  • Never hide uncertainty — every automated claim is sourced and confidence-scored, escalated rather than papered over.
