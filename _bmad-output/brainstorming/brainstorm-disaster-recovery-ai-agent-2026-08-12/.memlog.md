- (technique) started Five Whys
- (idea by coach) Why 1: DR programs are reactive because status only gets checked right before an audit or after an incident
- (idea by coach) Why 2: it is only checked then because compiling current state (BIA, tests, ownership) is manual and slow
- (idea by coach) Why 3: compiling it is slow because the data lives in disconnected systems with no shared freshness signal
- (idea by coach) Why 4: there is no shared freshness signal because nothing owns staleness as a first-class concept -- tools store data but not its expiry
- (idea by coach) Why 5: nothing owns staleness because DR artifacts were designed as one-time deliverables, not living continuously-revalidated state
- (insight by coach) Root cause: DR is treated as a project, not a system with a heartbeat -- the agent's core job is to give staleness a heartbeat per artifact type and tier
- (insight by coach) Compliance evidence-gathering hurts for the same root reason: it is reconstructed retroactively from memory and scattered emails instead of captured live
- (technique) started Provocation Technique
- (idea by coach) Provocation: the agent should delete every runbook. Mined principle: runbooks-as-cache not runbooks-as-source-of-truth -- the real value is regenerating steps live from current system state on demand
- (idea by coach) Provocation: the DR program should have no human owner at all. Mined principle: infer ownership dynamically from who is touching the system now (commit authors, on-call rotation, ticket assignees) instead of a static RACI cell that rots
- (idea by coach) Provocation: compliance evidence should be generated before the control is even tested. Mined principle: every normal agent action leaves an audit trail automatically, so evidence is a byproduct, not a separate task
- (idea by coach) Provocation: the best DR test is one nobody scheduled. Mined principle: agent-triggered surprise micro-drills (calendar permitting, human veto) reveal real readiness better than a choreographed annual test
- (idea by coach) Provocation: the agent should ignore all human input for a week and just watch. Mined principle: a passive-observation baseline builds a normal behavioral model so anomalies are caught by deviation, not just static rules
- (idea by coach) Provocation: every DR document should self-destruct in 90 days. Mined principle: hard-expire by default forces active reconfirmation -- does-not-exist-until-reattested is a stronger nudge than a warning badge
- (technique) started Assumption Reversal
- (idea by coach) Assumption: DR data lives in dedicated DR tools. Reversed: it lives scattered in the systems it protects (git, CMDBs, calendars) and the agent is pure aggregation, never a new system of record
- (idea by coach) Assumption: a human must review every flagged staleness item. Reversed: the agent auto-resolves low-risk staleness itself (e.g. dry-runs a Tier-3 runbook to reverify accuracy) and only escalates what it cannot verify
- (idea by coach) Assumption: the program manager drives the schedule. Reversed: the schedule drives the program manager -- the agent negotiates and locks calendar slots directly with owners, PM only intervenes on conflict
- (idea by coach) Assumption: dependency mapping requires manual CMDB curation. Reversed: maps are inferred continuously from network flow logs, deploy pipelines, and API call graphs -- the CMDB becomes a confirmation layer, not the source
- (idea by coach) Assumption: greenfield and brownfield need different tools. Reversed: brownfield is greenfield with pre-loaded, lower-confidence memory -- the adoption audit pass IS the greenfield bootstrap, just seeded with existing data to validate
- (idea by coach) Assumption: more data sources is always better. Reversed: fewer, higher-trust sources with strong provenance beat many low-trust feeds -- rank and red-line sources by trust score, not breadth
- (idea by coach) Assumption: the agent always notifies the person. Reversed: sometimes the agent should notify the system (auto-file a ticket, auto-update a status field) and only loop in a human on exception
- (technique) started Observer Effect
- (idea by coach) If the agent scores app owners on responsiveness, owners may game the metric with fast empty acknowledgements rather than genuinely engaging
- (idea by coach) Once dependency mapping is visible and shared, teams may deliberately hide or under-document risky dependencies to avoid being flagged as a blocker
- (idea by coach) Once a staleness score exists and is watched, teams optimize the score (touch the doc to reset a timestamp) rather than the underlying accuracy -- must detect refreshed-but-not-reviewed via content diff, not just mtime
- (idea by coach) Simply installing a DR agent that watches everything may itself raise perceived audit pressure and change how honestly people log incidents -- needs transparent, non-punitive framing or it corrupts its own data
- (idea by coach) The daily catch-up ritual itself may narrow DR maturity to whatever the agent's brief measures -- scope creep toward the instrumentable, not the important
- (idea by coach) If leadership sees a shiny DR maturity score rise, budget/attention for DR might paradoxically decrease because it is handled now -- the dashboard's success could starve its own resourcing
- (idea by coach) Publishing a dependency graph might reveal politically inconvenient ownership gaps (two teams each think the other owns something) -- needs a diplomatic communication layer, not a raw graph dump
