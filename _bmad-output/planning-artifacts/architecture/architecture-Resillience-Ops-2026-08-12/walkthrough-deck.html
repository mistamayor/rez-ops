REZ OPS — Architecture Walkthrough
Sensors — Ledger — Voice

REZ·OPS

Smoke detector, not fire inspector.

An AI agent framework that keeps a Disaster Recovery program's true state — freshness, ownership, risk — continuously visible, without becoming yet another system of record.

ARCHITECTURE SPINE WALKTHROUGH · v1 · 2026-08-12
The Problem

Reactive by design, not by accident

DR programs only get inspected when it's expensive to do so.

  • Fragmented data. BIAs in SharePoint, tiering in a CMDB, runbooks in wikis, RACI in a spreadsheet nobody re-syncs.
  • No system knows its own freshness. A BIA doesn't know it's 18 months overdue. A RACI's "Accountable" owner left the company two reorgs ago.
  • Ownership rots silently. Nothing infers who's actually responsible today from what's actually happening — only from a document that stopped being updated.
  • Assembly is manual and slow — so true state only gets compiled under pressure: right before an audit, or right after an incident already proved a gap was real.
Where today's cycle breaks
incident or audit looms
  → scramble to reconstruct state
  → gaps found too late
  → fixed under duress
  → drifts stale again
  → (repeat)
At global, always-on scale, that lag is where real risk hides: a stale Tier-1 BIA or an unmapped dependency turns an outage into a disaster.
The Paradigm

Sensors — Ledger — Voice

Three layers, each its own MCP-server boundary. One dependency-direction rule holds it together.

Sensors

One dumb, read-only, domain-scoped MCP server per data source (calendar, ticketing, git, CMDB).

Fetches and normalizes only — carries zero freshness, confidence, or ownership logic.

Ledger

One MCP server, sole owner of the Freshness Ledger.

Computation, confidence/coverage scoring, ownership arbitration, orphan-risk detection, drafted outbound content — all in one place.

Voice

The orchestrating runtime (Claude Code, or any MCP client). Calls Sensors and Ledger, presents output.

Holds no domain logic of its own — that's exactly what keeps Rez Ops portable across runtimes.

Decisions — Boundary & Topology

Where the walls are

AD-1 · AD-2 · AD-6 — keeping domain logic, server scope, and outbound writes each in exactly one place.

AD-1 · Layering discipline

Domain logic (freshness rules, confidence, ownership inference) may only live inside a connector or ledger-core tool — never in a runtime prompt, skill, or system instruction.

Prevents: freshness/confidence/ownership logic leaking into runtime-specific prompts, which breaks consistency and cross-runtime portability. Enforced by code review, not tooling.

AD-2 · One server per domain

Every data domain ships as its own minimal MCP server. A new domain means a new connector — never extending an existing one's scope. Tool names are domain-prefixed (calendar_list_items).

Prevents: a monolith server bloating every session's tool/context budget, and two independently-built connectors colliding on tool names in the runtime's shared namespace.

AD-6 · Draft-not-send

Any agent-authored outbound content is written only to a git-tracked drafts/ queue, and only by calling ledger-core's write tool — never a direct filesystem write from any other component.

Prevents: an accidental or later-added write-back path bypassing human approval, and two writers racing on one drafts directory.

Net effect: no component can quietly grow a responsibility it wasn't designed to hold.
Decisions — Schema, State & Ownership

One truth, one owner, no guessing

AD-3 · AD-4 · AD-5 · AD-9 · AD-10 — the rules that make the Ledger trustworthy.

AD-3 · Append-only, projected

Every state change is an immutable, timestamped, git-committed event. Current state is always a recomputed projection — never hand-edited.

Prevents: silent, unaudited edits to freshness/ownership state that would destroy the history the trust layer depends on.

AD-4 · One shared schema module

A single versioned schema defines every record shape. Every connector and ledger-core import it — none declares ad hoc fields.

Prevents: each connector inventing its own shape for observed data, producing facts ledger-core can't merge.

AD-5 · Ledger-core owns confidence

Confidence/coverage is computed exclusively by ledger-core, from raw connector facts, using one documented method. Connectors never report a confidence score.

Prevents: connectors independently guessing confidence with inconsistent methodology — undermining "never hide uncertainty."

AD-9 · RawFact vs. LedgerRecord

RawFact (connector-writable): raw data + a source reference, never a confidence value. LedgerRecord (ledger-core-only): confidence, tier_sla, escalation_owner, last_verified — all computed.

Prevents: connectors asserting owned fields like tier_sla, and loss of the provenance trail compliance/CISO adoption needs.

AD-10 · Ownership arbitration

Exactly one authoritative connector per ownership-bearing field per entity. Conflicting facts are logged, never overwrite. Total silence escalates the field to confidence: unknown and adds the entity to the orphan-risk list.

Prevents: silent last-write-wins conflicts, and the ownership wedge feature staying unimplemented prose instead of a real rule.

Decisions — Operational Envelope

Runs on a laptop, fails safe

AD-7 · AD-8 — the two rules that bind every layer, without exception.

AD-7 · Local-first envelope

No hosted database, no container orchestration, no persistent server process. Durability comes from a git remote, pushed after each session.

  • Scheduled work: OS scheduler (cron/launchd) invokes claude -p --mcp-config .mcp.json --output-format json — never --bare, which skips MCP autodiscovery and would run with zero Sensors or Ledger attached.
  • A failed scheduled run appends an error entry to _ops.log.md — never fails silently.
  • Credentials: OS keychain or REZOPS_{DOMAIN}_TOKEN — never rezops.config.yaml or any git-tracked file.
AD-8 · Graceful degradation

Every runtime-facing operation fails open. An outage surfaces as an explicit unknown/unverified state — never a crash that blocks the human.

Prevents: Rez Ops ever blocking, replacing, or degrading the DR program below today's manual baseline if it's itself wrong, down, or a connector fails.

No component or decision may require Rez Ops to be running for the underlying DR program to function. It is additive observation, never a dependency.

Deferred, Not Forgotten

What we're deliberately not doing yet

Every deferral ties back to a brief constraint or an immaturity signal — not an oversight.

Briefing delivery channel (Slack, email, terminal)
Already scoped as a swappable view over the same model — decide on first real usage, not in the abstract.
Write-back / auto-actioning against systems of record
Human-approval non-negotiable comes first, per the brief; AD-6 keeps the boundary ready for it, not built yet.
MCP SDK v2 migration
v2.0.0 GA shipped 2026-07-28 — about two weeks old at spine time. Too new to commit to; revisit once it settles.
Packaging — personal config vs. installable product
Explicitly left open by the brief; not a decision this spine forces.
Multi-user / multi-tenant support
v1 is single-owner by design, per the brief's stated primary user.
Closing

Back to the non-negotiables

Every architectural decision earns its place by operationalizing one of the brief's three commitments.

Read-only-firstSensors only fetch and normalize. AD-6's draft-not-send boundary blocks any write path from existing, even by accident.
Never hide uncertaintyAD-5/AD-9 make confidence computed and explicit; AD-10 escalates silence to unknown and an orphan-risk entry, never a guess.
Graceful degradationAD-8: Rez Ops is additive observation. If it's wrong or down, the program falls back to today's baseline — never worse off.
