# Adversarial Review — AD-13/AD-14/AD-15 (design-only pass, 2026-09-05)

**Method:** for each pair below, two engineers each read only the spine — AD-13, AD-14, AD-15, and whatever AD-1–AD-12 language they explicitly cite — and each implements a unit one level down (a future story building one Executor, or one piece of the approval/execution-recording machinery) that satisfies every AD it is bound by *to the letter*. The two units still build incompatibly, or one alone is unenforceable exactly as written. Each pair closes with the AD (new or tightened) that would have prevented it.

**Verdict:** AD-13/14/15 correctly separate proposal, approval, and execution into three distinct concerns, but the pass that specified *what* must happen at each step never specified *through what mechanism* — there is no re-fetch tool, no approver-identity model, no execution-slot reservation, and no exclusive-ownership rule for which Executor handles which action, and the one invariant the whole layer exists to protect ("only a deliberate, explicit human... ever executes anything") has no technical enforcement at all, only an assertion two implementers can read as literally licensing the opposite of what it intends. Seven holes found; the two most serious (Pairs 2 and 7) both mean AD-14's human-approval gate and AD-13's human-invocation gate are, as currently specified, satisfiable by Voice acting entirely alone.

## Pair 1 — "Re-fetches its target `ActionProposal` from ledger-core": no tool exists, and none of the existing ones fit (CRITICAL)

**Unit A — Story 17, "ServiceNow Ticket Executor":** engineer reads AD-13's rule ("an Executor re-fetches its target `ActionProposal` from ledger-core") together with AD-2 ("every tool name domain-prefixed") and concludes a new get-by-id tool is required, since none of the shipped `ledger-core` tools (`ledger_get_record`, `ledger_list_records`, `ledger_get_briefing`, `ledger_get_coverage`, `ledger_list_drafts`, `ledger_create_draft`, `ledger_ingest_raw_fact`) can address an `ActionProposal` — AD-12 says explicitly "proposals aren't themselves an artifact type in the `RawFact` sense," so `ledger_get_record(artifact_type, artifact_id)`, which reads `ledger_data/{artifact-type}/{artifact-id}.yaml` per the Naming Conventions table, structurally cannot resolve one (there is no `action_proposals/` per-artifact-type directory — only the flat `action_proposals.log.md`). Story 17 adds `ledger_get_action_proposal(proposal_id)`, which projects the flat log server-side (same projection logic AD-12 already requires) and returns the current `proposed`/`decided`/`approved` state as one object.

**Unit B — Story 18, "Runbook-Rotation-Reminder Executor":** engineer reads AD-13's own "Prevents" clause the other way — "ledger-core itself never gains per-vendor write code and remains the sole writer to `ledger_data/`" — and notices this constrains *writes*, not reads. Since `ledger_data/` is a git-committed, plaintext, local-first directory (AD-3, AD-7) and Executors already run as local processes with filesystem access (unlike Sensors/Voice, which only ever go through MCP tool calls), Story 18's Executor "re-fetches" its target proposal by opening and parsing `ledger_data/action_proposals.log.md` directly, re-implementing the proposed/decided/approved projection inline in the Executor's own code rather than calling any `ledger-core` tool at all.

**The clash:** both units satisfy AD-13's literal sentence ("re-fetches its target `ActionProposal` from ledger-core" is compatible with "re-fetches the file ledger-core writes," if "from ledger-core" is read as "from ledger-core's data," not "via a ledger-core tool call"). But Story 18 now has its own, independently-maintained copy of the proposed/decided/approved projection logic, sitting outside `ledger_core/` — exactly the per-vendor domain-logic leak AD-1 and AD-2 exist to prevent, just relocated to the read side. If ledger-core's own projection logic is ever corrected (e.g. the duplicate-`decided`-event corruption handling Story 13 prompted, per AD-15's own Prevents clause), Story 18's Executor silently keeps using the old, unpatched logic — the two Executors can disagree about a proposal's current `policy_decision` or approval state from the same underlying log. AD-13's "Prevents" clause literally names this risk ("an Executor bypassing the MCP-tool-boundary discipline every other component follows") but the Rule text never forecloses it — it only describes what the Executor must confirm, not how it may access the data to confirm it.

**Root gap:** every other cross-component read in this spine goes through a named tool (`ledger_get_record`, `ledger_get_briefing`, etc.) — AD-2 makes the tool boundary structural for every other component. AD-13 is the first AD to describe a required read without naming, or even mandating the existence of, the tool that serves it.

**Close with:** tighten AD-13 to state explicitly: *an Executor's re-fetch of its target `ActionProposal` MUST go through a new, dedicated ledger-core tool (e.g. `ledger_get_action_proposal`) that returns the fully-projected proposed/decided/approved state — an Executor never reads `action_proposals.log.md` (or any `ledger_data/` file) directly.* This is the write-side's AD-2 boundary, stated on the read side too, and it should be added as a named tool in the Structural Seed alongside the other "new ledger-core tool" callouts AD-12/14/15 already promise.

## Pair 2 — `approved`'s authorization model: Voice can supply its own "approver" (CRITICAL)

**Unit A — Story 19, "Interactive Approval Gate":** engineer reads AD-14's Prevents clause ("collapsing 'who approved this' into 'who happened to invoke execution'") as requiring a channel Voice cannot originate on its own. Implements the new `ledger_approve_action_proposal` tool so it is registered, but documents (as a build convention, since the spine specifies no mechanism) that it is only ever to be invoked after the runtime displays the pending proposal and requires the human to type a distinct confirmation phrase back — the tool call's `approver` argument is filled from that literal confirmation transcript, not from Voice's summary of the conversation.

**Unit B — Story 20, "Fast-Path Approval":** engineer reads AD-14's Rule exactly as written — "a `requires_approval` `ActionProposal` needs a new `approved` event (who approved it, when)... via a new ledger-core tool" — and finds no field-level or process-level constraint on how `approver` is populated. Implements `ledger_approve_action_proposal(proposal_id, approver: str, note: str | None)` as an ordinary MCP tool, callable by Voice exactly like `ledger_create_draft` or any AD-11/12 tool. Voice, mid-conversation, infers from context ("the user said 'yes go ahead with all of these'") that approval was given, and calls the tool itself with `approver="Olu Adeogun"` — no distinct human-authored confirmation ever reaches ledger-core; the only evidence approval happened is Voice's own tool call.

**The clash:** both tools have an identical signature and both literally satisfy AD-14 ("a new `approved` event... appended... via a new ledger-core tool") — the AD never specifies who is allowed to call the tool, never requires the `approver` value to be independently verifiable (an OS-keychain identity, a signed token, anything AD-7's existing credential model could anchor to), and never says the tool must reject a call it cannot attribute to a distinct human action. Unit B is not a misreading — it is the more literal implementation, since Unit A's extra confirmation-transcript discipline is pure convention the spine never asks for. Under Unit B, Voice — the component AD-1 insists "holds no domain logic" and "never computes... policy" — has just supplied the one input (`approver`) that makes a `requires_approval` proposal indistinguishable, on the log, from a genuinely human-approved one. This is the same class of loophole AD-11 already closed once (Voice self-supplying `confidence` to control AD-12's evaluation) — AD-14 reopens it one layer up, for the human sign-off step this whole layer exists to add.

**Root gap:** AD-14 specifies the event's *shape* ("who approved it, when") but not its *provenance guarantee* — nothing says the tool call must originate from something Voice cannot itself produce unaided. Every other ledger-core-computed value in this spine (`confidence`, `tier_sla`, `policy_decision`) is protected by "a caller-supplied value is a schema violation." `approved` has no equivalent: it is entirely caller-supplied by design (a human must supply *something*), but nothing distinguishes a genuine human-originated call from Voice inventing one on the human's behalf.

**Close with:** tighten AD-14 to specify a minimal provenance guarantee for the `approved` event — at minimum, name what `approver` must be anchored to (e.g. the OS user identity the runtime process is running as, per AD-7's existing credential-identity model, captured by the tool itself rather than passed as a free-text argument Voice fills in), and state explicitly that Voice may *relay* a human's approval into the tool call but the tool's own identity capture — not Voice's free-text argument — is what the event records. Absent this, AD-14 does not actually prevent the exact collapse ("who approved" vs. "who happened to invoke") its own Prevents clause names.

## Pair 3 — Idempotency check-then-act is not atomic: two racing invocations both execute (CRITICAL)

**Unit A — Story 17 (cont'd), single-session assumption:** engineer reads AD-13's "only a deliberate, explicit human... invocation of one specific `proposal_id`" as an implicit concurrency guarantee (one human, one action, one moment) and implements AD-15's rule literally and minimally: read `action_executions.log.md`, filter to `proposal_id`, if no successful attempt exists, perform the external write, then append the outcome event. No lock, no reservation.

**Unit B — Story 21, "Retry-Safe Executor Base":** engineer reads AD-3's append-only/projection discipline plus AD-7's local-first, git-committed persistence and reasons that two Executor invocations against the same `proposal_id` (a human double-invoking after a slow first call looks hung, or two Voice sessions on two machines pulling the same git-synced `ledger_data/`) are exactly the kind of race AD-3's audit-log model must survive. Implements a two-phase pattern: append an `attempt-started` event *before* performing the external write (claiming the slot), and only proceeds if no other `attempt-started`/`success` event for that `proposal_id` already exists at claim time.

**The clash:** AD-15's Rule — "before executing, an Executor checks this log for the target `proposal_id`: one already carrying a successful attempt is never executed again" — describes a check against *past* attempts; it does not require the check-and-claim to be a single atomic step relative to a concurrent second invocation. Feed both units the identical race (two invocations of the same `proposal_id` within the same second, e.g. one human hits "execute" twice, unsure the first one registered): Unit A's Executor reads zero prior attempts *twice*, performs the external write *twice* (e.g. `create_ticket`, which is not naturally idempotent — two calls create two tickets against one proposal), and only then records two successful attempts — the idempotency guarantee AD-15 exists to provide has already been violated by the time either write to the log happens. Unit B does not. Both satisfy AD-15's literal words.

A second, related gap in the same clause: AD-15 never states what happens if an Executor crashes *after* the external write succeeds but *before* the outcome event is recorded — the log then shows zero attempts (identical to "never tried"), and a subsequent, fully-correct retry (per either unit's logic) re-executes an already-completed, non-idempotent external action. "One already carrying a successful attempt is never executed again" is airtight only if every successful attempt is guaranteed to be recorded — AD-15 asserts the check, not the guarantee that makes the check sufficient.

**Root gap:** AD-15 specifies the log's *read* discipline (check before executing) but not a *claim/reservation* discipline (make the check-and-commit atomic, or externally correlate the write with an idempotency key the target system itself can dedupe on). Unlike AD-3's log-writing rule, which is airtight for ledger-core because ledger-core is the sole writer to one log from one process per session, AD-15 hands the same discipline to an unspecified number of independently-built Executor processes with no arbitration mechanism at all.

**Close with:** tighten AD-15 to require a two-phase pattern — an Executor appends an `attempt-started` (or equivalent claiming) event *before* performing the external write, and treats any existing `attempt-started`/`success` event for that `proposal_id` (not just `success`) as blocking a new attempt — plus, where the target system supports it, passing a stable idempotency key (e.g. derived from `proposal_id`) so a crash-before-recording failure mode is caught by the external system too, not just by ledger-core's own log.

## Pair 4 — No exclusive-ownership rule for which Executor handles which action (HIGH)

**Unit A — Story 17 (cont'd):** builds `executors/ticketing/`, registering a tool that performs `create_ticket` against ServiceNow — matching the Deferred section's named first target exactly, and matching the Structural Seed's `executors/ticketing/` example.

**Unit B — Story 22, "ServiceNow-Native Executor":** independently reads AD-13's rule — "one per action type/vendor, mirroring Sensors' one-server-per-domain pattern" — and, since the *vendor* is ServiceNow rather than the abstract domain "ticketing," builds `executors/servicenow/`, also registering a tool that performs `create_ticket` (same action key, same external system), reasoning that "vendor" rather than "domain" is the correct AD-2-mirroring granularity for a component this vendor-specific (its credentials, per AD-13, are already vendor/action-scoped, not domain-scoped like a Sensor's).

**The clash:** AD-13's phrase "one per action type/vendor" reads as a single granularity to one implementer and a choice between two different granularities to another — nothing says which, or that only one Executor server may ever claim authority over a given `action` value. Unlike AD-10, which assigns "exactly one authoritative connector per ownership-bearing field per entity" for read-side conflicts, AD-13 has no equivalent rule for the write side: nothing stops both `executors/ticketing/` and `executors/servicenow/` from existing simultaneously, both correctly re-fetching the proposal, confirming policy, and writing to the same underlying ServiceNow instance. If a human (or Voice, per Pair 7 below) invokes both against the same `proposal_id` — even sequentially, not just concurrently as in Pair 3 — AD-15's idempotency log is the only shared checkpoint, and only if both Executors are built against the same log-checking discipline (which Pair 3 already shows isn't guaranteed).

**Root gap:** AD-2's "never two connectors colliding on tool names" protects the read side by fixing one server per domain; AD-13 asserts the same pattern for writes ("mirroring Sensors' one-server-per-domain pattern") but never says which axis (action-type, vendor, or the conjunction of both) is the actual uniqueness key, and provides no arbitration rule analogous to AD-10 for when two Executors both claim it.

**Close with:** tighten AD-13 to fix the granularity explicitly — most consistent with AD-2's "domain-prefixed tool name" convention: exactly one Executor server per `action` value (the same fixed vocabulary AD-12 already defines from `rezops.policy.yaml`'s top-level keys), never per vendor independently of action — and state that a second Executor registering a tool for an `action` another Executor already serves is a build-time/registration error, the write-side analogue of AD-10's ownership map.

## Pair 5 — "`policy_decision` is favorable": not a schema value, and the `requires_approval` carve-out can be silently skipped (MEDIUM-HIGH)

**Unit A — Story 17 (cont'd):** implements the check as two sequential conditions exactly as AD-13's parenthetical lays them out: first, `policy_decision != "denied"`; second, if `policy_decision == "requires_approval"`, additionally confirm an `approved` event exists — an `automatic` proposal skips the second check, a `requires_approval` proposal without approval is rejected with a distinct "not yet approved" error, distinguishable from a `denied` rejection.

**Unit B — Story 23, "Minimal Executor Base":** implements "confirms `policy_decision` is favorable" as a single up-front gate, reading `automatic` as the only value that is unconditionally "favorable" and reasoning that `requires_approval`'s parenthetical is a separate, secondary elaboration rather than a carve-out of the same gate. Story 23's Executor's primary favorability check treats anything other than `automatic` (i.e. both `denied` and `requires_approval`) as "not favorable" and returns a single generic rejection — and, because that rejection happens before the code ever reaches the "(for `requires_approval`) that an `approved` event exists" clause, the approval-checking branch is simply never implemented at all. A later-approved `requires_approval` proposal is, in this Executor, permanently indistinguishable from a `denied` one and can never execute.

**The clash:** both units satisfy "an Executor... confirms `policy_decision` is favorable and (for `requires_approval`) that an `approved` event exists" as literally written — "favorable" is a gloss, not one of the three defined `policy_decision` enum values (`automatic`/`requires_approval`/`denied`), so a second implementer has no schema anchor forcing the reading that `requires_approval`-plus-`approved` is *also* favorable. Story 23 fails closed (never executes a wrongly-favored proposal) but also never executes a correctly-approved one — a functional gap that looks, from the outside, identical to a `denied` proposal being (correctly) blocked, making the bug invisible without directly comparing two Executor implementations' source.

**Root gap:** "favorable" names a derived boolean the spine never defines against the actual three-valued enum; every other AD in this spine that introduces a derived check (AD-9's `confidence` enum, AD-12's `policy_decision` enum itself) spells out the exact values, and this is the first place a *combination* of an enum value and a separate event's existence needs to be tested — with no explicit truth table.

**Close with:** tighten AD-13 to replace "confirms `policy_decision` is favorable" with an explicit two-row truth table: `automatic` → proceed; `requires_approval` with a matching `approved` event → proceed; `requires_approval` with no `approved` event → reject (distinct from denied); `denied` → hard-reject, no override (AD-14). Removing "favorable" as an undefined intermediate term closes the gap.

## Pair 6 — Can a second (or misplaced) `approved` event land on the log at all? (MEDIUM)

**Unit A — Story 19 (cont'd):** builds `ledger_approve_action_proposal` to validate the target proposal's *current projected state* before appending: it re-derives `proposed`/`decided`/(any prior `approved`) from the log first, and refuses the call outright — no event appended — if the proposal isn't currently `requires_approval` with no existing `approved` event (i.e. rejects approving a `denied` or `automatic` proposal, and rejects a second approval of an already-approved one).

**Unit B — Story 20 (cont'd):** builds the same tool as a thin, unconditional append: whatever `proposal_id`/`approver` arguments arrive, an `approved` event is written to `action_proposals.log.md`. Validation, in this reading, is the *reader's* job (an Executor, or a future dashboard) — consistent with how AD-12 itself describes the tool that creates a proposal as validating at creation time, but AD-14 never states the equivalent obligation for the approval tool.

**The clash:** AD-14 says "like `decided`, `approved` is a one-time state change per proposal, not a repeatable attempt" — but only to justify *where* the event lives (the same log, not AD-15's retry-aware one), never to state that the tool itself must enforce one-time-ness or state-appropriateness. Under Unit B, a network-timeout retry (the caller unsure whether the first `ledger_approve_action_proposal` call landed) can legally produce two `approved` events with two different `approver` names, and nothing stops an `approved` event from being appended to a `denied` or `automatic` proposal, producing a misleading audit record any tool that only checks "does an `approved` event exist" (rather than replaying the full state machine) would misread as legitimate approval — for a proposal AD-14's own next sentence says must be "hard-blocked at the Executor... regardless of who invokes it." The hard-block still holds *if* every Executor is built like Unit A of Pair 5, but the log itself is now internally inconsistent, which is exactly the "audit distinction the whole evidence/policy layer exists to provide" AD-14's Prevents clause names.

**Root gap:** AD-12 (for `decided`) and AD-15 (for a second `decided` event) are both explicit that "corruption" is a named, checked-for condition. AD-14 imports the same "one-time state change" language for `approved` without importing the equivalent enforcement obligation — leaving whether a second/misplaced `approved` event is corruption-to-reject or just-another-log-line entirely up to the implementer.

**Close with:** tighten AD-14 to state explicitly that `ledger_approve_action_proposal` re-derives the proposal's current projected state before writing, and rejects the call (no event appended) unless the proposal is currently `requires_approval` with no existing `approved` event — making a duplicate or misplaced `approved` event a rejected call, not a corrupt-but-accepted log line, the same discipline AD-12/AD-15 already apply to `decided`.

## Pair 7 — "Only a deliberate, explicit human... invocation" has no enforcement mechanism at all (CRITICAL)

**Unit A — Story 17 (cont'd), out-of-band gate:** reads "only a deliberate, explicit human (or Voice, on explicit human instruction) invocation of one specific `proposal_id` ever executes anything" as requiring a channel that structurally cannot be satisfied by Voice's own initiative. Implements `execute(proposal_id)` as a tool the Executor server registers but the *runtime's* `.mcp.json`/tool-permission layer restricts so that Voice may only call it after the human has separately, out-of-band (e.g. a distinct terminal prompt the Executor itself controls, not mediated by Voice's conversation) confirmed the specific `proposal_id` — mirroring the spirit of AD-1's "enforced by code review, not tooling... but read-only by default; action is an explicit, separately-gated capability" language used for AD-11/12.

**Unit B — Story 24, "Conversational Execute":** reads the same sentence at face value: it explicitly licenses "Voice, on explicit human instruction" as sufficient, alongside a human invoking it directly — and nothing else in AD-13, AD-14, or AD-15 places any technical precondition on *that* path distinct from Voice's own judgment that the human gave "explicit instruction." Story 24 registers `execute(proposal_id)` as an ordinary MCP tool, identical in shape and permission to every other tool Voice already calls (`ledger_create_draft`, `ledger_get_briefing`, etc.). Voice, mid-session, decides from conversational context that the human's "yes, go ahead" instruction was explicit enough, and calls `execute(proposal_id)` itself.

**The clash:** Unit B is not a misreading — AD-13's own text names "Voice, on explicit human instruction" as one of the two things that "ever executes anything," and specifies no technical control (a confirmation token, an out-of-band channel, a permission scope the Voice session cannot self-grant) that would distinguish genuine human instruction from Voice's own good-faith (or compromised, or hallucinating, or prompt-injected) inference that instruction occurred. Every other guarantee this spine protects is enforced structurally — a schema rejects a caller-supplied `confidence`/`tier_sla`/`policy_decision` (AD-5/AD-9/AD-12); a tool boundary keeps domain logic out of connectors (AD-1/AD-2). "Only a deliberate, explicit human... invocation... ever executes anything" is the one invariant in the entire spine enforced by nothing but Voice's own self-report that a human told it to — which is precisely the shape of trust AD-1 exists to rule out ("Voice holds no domain logic... this is what keeps Rez Ops portable" and "enforced by code review, not tooling" for domain logic specifically call out that *something* concrete must enforce every other guarantee).

**Root gap:** AD-13 states the invariant as a description of who is allowed to trigger execution, not as a rule about what mechanism the Executor (or the runtime) must use to verify that a given `execute(proposal_id)` call actually followed genuine, contemporaneous human instruction rather than Voice's own initiative. Without that mechanism, "Voice, on explicit human instruction" is textually indistinguishable, at the tool-call boundary, from "Voice, on its own initiative" — the exact collapse the rest of the spine works hard to prevent one layer down (AD-11's evidence-confidence loophole, AD-14's approver loophole in Pair 2 above).

**Close with:** tighten AD-13 to name a concrete mechanism the Executor (not Voice, and not a documentation convention) enforces — at minimum, requiring `execute(proposal_id)` calls to carry a fresh, human-originated confirmation the runtime captures independently of Voice's own conversational judgment (e.g. a short-lived confirmation code shown to the human alongside the pending proposal, that only a human copying it back — never Voice inferring intent — can supply), and stating explicitly that a bare, Voice-authored belief that "the human said go ahead" is not sufficient grounds for the tool to accept the call. Absent this, AD-13's central guarantee is aspirational text, not an enforced boundary — the one place in the whole Executor design where a compromised or careless Voice session has a straight, spec-compliant path to a real external write.

## Direct answers to the four flagged questions

- **Does AD-13's re-fetch imply a tool that doesn't exist yet, and could two Executors resolve it differently?** Yes on both counts — see Pair 1. No shipped or specified `ledger-core` tool can address an `ActionProposal` by id (it isn't stored in the per-artifact-type shape `ledger_get_record` reads), and AD-13's Rule never mandates the new tool's existence, leaving a direct-file-read implementation just as literally compliant — and structurally dangerous, since it relocates proposal-state projection logic outside `ledger_core/`.

- **Is `ledger_approve_action_proposal`'s authorization model specified — could Voice supply a fake "approver"?** No, and yes — see Pair 2. AD-14 specifies the event's shape but nothing about who may call the tool or how `approver` is attributed; a literal, spec-compliant implementation lets Voice populate `approver` from its own inference that a human approved, with no independent confirmation channel required.

- **Is "successful attempt" precise against a concurrent-execution race?** No — see Pair 3. The check-then-act sequence is not required to be atomic, so two invocations of the same `proposal_id` (a genuine race, or a human's own uncertain double-invocation) can both pass the "no successful attempt yet" check before either records an outcome, and a crash between a successful external write and its logged outcome produces the identical "never attempted" signal a subsequent retry would act on.

- **Is "only a deliberate, explicit human... invocation... ever executes anything" actually enforceable given Voice calls the tools?** No — see Pair 7. AD-13's own text licenses "Voice, on explicit human instruction" as sufficient, and specifies no mechanism distinguishing that from Voice's own initiative at the point `execute(proposal_id)` is actually called. Unlike every other guarantee in this spine (enforced by a schema rejecting caller-supplied derived values, or a tool boundary excluding domain logic from connectors), this one currently rests entirely on Voice's self-report — the same trust-Voice framing AD-1 exists to rule out, reopened at the one step with irreversible real-world consequences.
