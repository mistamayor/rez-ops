## Findings

1. **[Info / reality-checked, not a gap] ServiceNow as the Deferred section's "first real target" is not an unverified assertion — it's already load-bearing, tested code in this repo.** `grep -rn -i servicenow` across the repo turns up two shipped, reviewed connectors (`connectors/ticketing/server.py`, `connectors/cmdb/server.py`, both `status: done` per `stories.yaml` and `deferred-work.md`) that already call ServiceNow's real Table API (`GET /api/now/table/{table}/{sys_id}`) over `httpx`, plus a landscape-research note in the original brief's addendum confirming ServiceNow's continued market presence as an incumbent DR/BCM vendor. The spine's claim that "this project already has a proven read-only integration to mirror the auth/HTTP pattern from" is therefore not a training-data assertion at all — it's a true statement about this codebase's own history, the strongest form of reality-check available. No action needed.
   Sources: repo greps of `connectors/ticketing/server.py`, `connectors/cmdb/server.py`, `_bmad-output/specs/spec-rez-ops/stories/5-ticketing-connector-servicenow.md`, `_bmad-output/specs/spec-rez-ops/stories/7-cmdb-connector-servicenow.md`, `_bmad-output/planning-artifacts/briefs/brief-Resillience-Ops-2026-08-12/addendum.md`

2. **[Low, documentation gap rather than an error — same category as the prior pass's Finding 2] AD-13/14/15's approval-and-idempotency design doesn't note whether MCP's own native tool-annotation and idempotency-adjacent primitives were considered and found insufficient.** A fresh web search (Sept 2026) confirms the MCP spec is still at the 2026-07-28 stateless revision — no newer spec has shipped — and that: (a) tool annotations (`destructiveHint`, `idempotentHint`, etc.) remain available in the pinned SDK and are the standard vocabulary for flagging a write-capable/destructive tool; (b) **the core protocol itself defines no idempotency key** — "whether a retry duplicates a payment, a deployment, a message, or a deletion depends entirely on whether the tool underneath was written to notice... idempotency remain[s] application responsibilities" (per the MCP blog's own tool-annotation writeup). AD-15's bespoke "check the log for a prior successful attempt before executing" mechanism is therefore squarely in the space the protocol explicitly leaves to the application — a defensible, arguably *necessary* choice, not a gap — but as with the AD-12 finding in the prior pass, the spine doesn't record that this was a deliberate decision rather than an oversight. Separately, the 2026-07-28 spec's mid-call confirmation flow (`elicitation`/`resultType: "input_required"`) changed shape from the older bidirectional `elicitation/create` stream to a stateless request/reissue pattern; AD-13/14's "confirms... an `approved` event exists" check is implemented as an ordinary ledger-core tool call rather than any protocol-level elicitation, so it is unaffected by and doesn't depend on that churn — worth stating explicitly so a future reader doesn't wonder whether the design assumes the older elicitation shape. Recommend a one-line addition to AD-13 or the Deferred section noting both of these were deliberate, protocol-version-agnostic choices.
   Sources: [Tool Annotations as Risk Vocabulary](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/), [The 2026-07-28 Specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/), [Key Changes — Model Context Protocol changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [MCP 2026-07-28 Specification Update Explained](https://blog.wu-boy.com/2026/09/mcp-2026-07-28-spec-update-en/)

3. **[Info] The `mcp` SDK `<2` pin and Stack table remain unchanged and unchallenged by AD-13/14/15.** The update adds no new row to the Stack table and asserts nothing that would require a different SDK version or capability than what AD-11/AD-12's pass already re-confirmed (same date, 2026-09-05). AD-13/14/15's Executor is "a new MCP server" in exactly the same sense as any existing connector — no new SDK feature (e.g. MRTR, `server/discover`, cacheable list results from the 2026-07-28 spec) is invoked or required by the design. No action needed.

4. **[Info] No greenfield-starter angle applies to this pass.** AD-13/14/15 don't touch scaffolding, a project generator, or any starter template's defaults — same conclusion as the prior pass's Finding 4, unchanged by this update.
